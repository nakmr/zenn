# なぜ R1CS と QAP を実装するのか？

Groth16 の検証は、最終的に **「ペアリングで多項式の等式を 1 点評価で確かめる」** という操作に集約されます。
そのためにはまず、証明したい計算（例えば「$x$ を秘密にしたまま $y = x^3 + x + 5$ を満たすことを示したい」など）を、 **多項式の等式の形** に翻訳しておく必要があります。

ただ、いきなり計算を多項式にするのは飛躍が大きすぎます。そこで、間に **R1CS（Rank-1 Constraint System）** という中間表現を挟みます。流れにすると、

1. 計算を **R1CS の制約の集合** に分解する
2. 制約の集合を **QAP（Quadratic Arithmetic Program）** = 多項式の組に畳む
3. 多項式の等式をペアリングで検証する（← 次回以降）

という三段ロケットです。
本章で実装するのは、このうち 1 と 2 にあたる部分です。前回作った Lagrange 補間もここで初めて実戦投入されます。スローガンにすると **「計算 → 制約 → 多項式の等式」** という流れですね。

:::message
- **R1CS = Rank-1 Constraint System**。「左辺どうしの積が右辺と等しい」を、**1 ステップにつき乗算 1 回** に正規化した制約形。詳しくは「学び 1」で扱います。
- **QAP = Quadratic Arithmetic Program**。R1CS を多項式環 $\mathbb{F}_p[x]$ の世界に「翻訳」したもの。詳しくは「学び 2」で扱います。
:::

# 実装中の気づき

## `CS_ONE = Variable(0)` という予約変数

最初に詰まったのは、「**定数加算 $a + 5$ を $A \cdot B = C$ の制約形にどう落とすのか？**」というところでした。

R1CS の制約 $A \cdot B = C$ における $A$、$B$、$C$ は、それぞれ変数たちの **係数つき和（線形和）** $\sum_j \alpha_j x_j$ の形です。ここに「$5$ を足す」を素直に書こうとすると、$\alpha_j$ にも $x_j$ にも当てはまらない、宙に浮いた定数項が出てきてしまいます。

解決策は、**インデックス 0 に「常に値 1 の変数」を予約しておく** ことでした。これを `CS_ONE = Variable(0)` と呼びます。値が常に $1$ なので、$5 = 5 \cdot \text{CS\_ONE}$ と書けます。つまり、定数項も **ふつうの線形和の項のひとつ** として扱えるようになります。

実装上は、制約系を作った直後に `init_one()` を 1 回だけ呼んで `assignments[0] = 1` を入れる慣習にしました。

```rust
pub fn init_one(&mut self, one: FieldElement) {
    if self.assignments.is_empty() {
        self.alloc_variable(); // Index 0 を確保
    }
    self.assign(CS_ONE, one);
}
```

これは bellman / arkworks / Circom といった Groth16 系の実装でも踏襲されている、業界共通の慣習のようです。

:::message
`CS_ONE` を予約しない世界線では、定数項を扱う **専用の制約ルール** が必要になり、$A \cdot B = C$ の対称性が崩れます。「**あらゆる定数を、CS_ONE の係数として線形和に乗せる**」という一手で API が大きく簡潔になる、という設計の知恵を感じました。
:::

## ゲートが「制約追加」と「Witness 計算」を同時に行う

`mul(a, b)` のような **ゲート関数** をどう設計するか、にもひとつ選択肢がありました。

- 案 A: 「制約を追加する処理」と「値を計算して埋める処理」を **別々の関数に分ける**
- 案 B: 1 つの `mul(a, b)` の中で、**新変数 `c` の確保 + `c = a * b` の値計算 + 制約 `(a)·(b) = (c)` の追加** をまとめてやる

最終的に案 B を採用しました。値計算と制約追加を分けると、「制約は通るのに値が違う」「値だけ正しくて制約が抜けている」といった整合性のズレが起きやすく、デバッグもつらくなります。

同時にやってしまえば、**「Witness は必ず制約を満たす」が手続きで自動的に保証** されます。Prover 側でいちいち整合性をチェックする必要もありません。

```rust
pub fn mul(&mut self, a: Variable, b: Variable) -> Variable {
    let c = self.alloc_variable();

    // 値の計算（Witness 生成）
    let val_a = self.assignments[a.0].as_ref().expect("variable a is unassigned");
    let val_b = self.assignments[b.0].as_ref().expect("variable b is unassigned");
    let val_c = val_a * val_b;
    self.assign(c, val_c);

    // 制約: (a) * (b) = (c)
    let mut lc_a = LinearCombination::new();
    lc_a.add_term(a, self.one());
    let mut lc_b = LinearCombination::new();
    lc_b.add_term(b, self.one());
    let mut lc_c = LinearCombination::new();
    lc_c.add_term(c, self.one());
    self.enforce(lc_a, lc_b, lc_c);

    c
}
```

# 学んだこと

## なぜ $A \cdot B = C$ という制約形なのか

R1CS の見た目は、よく考えると妙に制限的です。書けるのは **「乗算 1 回 + 線形和」** だけ。
たとえば $w = x \cdot y \cdot z$ のように **3 つの積をひとつの制約に押し込む** ことはできません。

$$
v_1 = x \cdot y, \quad w = v_1 \cdot z
$$

のように、**乗算 1 個ずつ 2 制約に分解** する必要があります。

なぜそんな縛りがあるのか? と最初は思いました。
これがやっと腹落ちしたのは、Layer 3 で扱う **ペアリング** が「乗算 1 回」しか提供できない、ということを知ったときです。

ペアリングというのは、ざっくり言うと

$$
e(g^a, g^b) = g^{ab}
$$

のように、**指数の上で積を 1 段だけ動かせる** 演算です。$a + b$ や $a \cdot b$ までは持ち上がりますが、$a \cdot b \cdot c$ までは 1 回では届きません。

つまり、**R1CS は「ペアリングで検証できる形」から逆算した、計算の正規形** だったということです。
「次数 1 ずつ積み上げる」と決めてしまえば、あとは多項式側でそれを揃えてあげればよい、という設計です。

具体例として、$y = x^3 + x + 5$ を R1CS に展開すると次のような流れになります。

1. $v_1 = x \cdot x$（乗算 1 回）
2. $v_2 = v_1 \cdot x$（乗算 1 回。ここで $x^3$ が出てくる）
3. $v_3 = v_2 + 5$（線形和、`add_const`）
4. $y = v_3 + x$（線形和、`add`）

乗算をひとつずつバラして、足し算は線形和に押し込んでいるのが見えると思います。
これが ZK の世界で言う **算術回路** の正規形で、 **「乗算ステップごとに 1 つの制約が立つ」** という構造になっています。

## 行列の「列」を Lagrange 補間して多項式に畳む

R1CS をそのまま並べると、**3 枚の行列**（$A$、$B$、$C$）になります。サイズはどれも「制約数 $\times$ 変数数」。
たとえば制約 3 本・変数 4 個なら、$3 \times 4$ の行列が 3 枚です。

ここから QAP へ変換するアイデアは、**「行列の列ごとに、Lagrange 補間で 1 本の多項式を作る」** というものです。

- 変数 $j$ の A 列を取り出すと、$(A_{0,j}, A_{1,j}, \dots, A_{n-1,j})$ という $n$ 個の数値ベクトルになる
- これを **補間点 $x = 0, 1, \dots, n-1$ における $y$ 値** とみなして、前回作った Lagrange 補間にかける
- 結果として、変数 $j$ に対する多項式 $a_j(x)$ ができる

同じことを B 列・C 列でもやるので、各変数 $j$ ごとに **3 本の多項式の組** $(a_j(x), b_j(x), c_j(x))$ が得られます。

```rust
pub fn from_r1cs(cs: &ConstraintSystem) -> Self {
    let num_vars = cs.next_var_index;
    let num_constraints = cs.constraints.len();
    let p = /* assignments[0] から法 p を取り出す */;

    let interpolate_column = |matrix: Matrix| -> Vec<Polynomial> {
        (0..num_vars)
            .map(|i| {
                let points = extract_column(cs, i, matrix);
                let dense = to_dense_vector(points, num_constraints, &p);
                Polynomial::lagrange_interpolation(&dense)
            })
            .collect()
    };

    Qap {
        a_polys: interpolate_column(Matrix::A),
        b_polys: interpolate_column(Matrix::B),
        c_polys: interpolate_column(Matrix::C),
    }
}
```

なぜこれで「制約の集合」が表現できるのか?
カラクリは、**$x = i$ における多項式の値が、ちょうど制約 $i$ 番目の係数そのもの** になっていることです。Lagrange 補間は補間点でちょうど指定の $y$ 値を取りますから、$a_j(i) = A_{i,j}$ になります。

つまり、「制約 $i$ 番目で変数 $j$ にかかっている係数」を知りたければ、**多項式 $a_j(x)$ に $i$ を代入する** だけでよい、という形に翻訳できたわけです。**行列の情報を、$n$ 本の多項式に圧縮できた** とも言えます。

実装上のささやかな罠もありました。各列はスパース表現 `[(行 index, 係数), ...]` で持っているので、Lagrange 補間に渡す前に **密ベクトルに展開** する必要があります。「ある制約にその変数が出ない」 = 「係数 0」を意味するので、$(i, 0)$ も明示的に渡さないと多項式がズレてしまうのです。

:::message
補間点を $0, 1, \dots, n-1$ にしておくと、次の「学び 3」で出てくる $Z(x) = \prod_i (x - i)$ の計算が楽になります。Lagrange 補間自体は任意の $n$ 個の異なる点で動きますが、整数の連番にしておくのが慣習です。
:::

## $h(x) \cdot Z(x)$ — 「全制約を満たす」を多項式の割り算で表す

ここが本章のクライマックスです。

QAP まで作れたら、Witness $s = (s_0, s_1, \dots, s_m)$ をかけて、各変数の多項式を **足し合わせます**:

$$
A_s(x) = \sum_j s_j \cdot a_j(x), \quad B_s(x) = \sum_j s_j \cdot b_j(x), \quad C_s(x) = \sum_j s_j \cdot c_j(x)
$$

すると、「Witness $s$ が全制約を満たす」という条件は、次のように書き換わります。

$$
A_s(x) \cdot B_s(x) - C_s(x) \text{ が } x = 0, 1, \dots, n-1 \text{ で } 0
$$

各 $x = i$ で 0 になる、というのは、補間点 $i$ における **制約 $i$ 番目** がきちんと $A_i \cdot B_i = C_i$ を満たしている、ということと同じです。

ここで前回の学び（多項式の根）が効きます。
**「補間点全部で 0 になる多項式は、$Z(x) = \prod_i (x - i)$ で割り切れる」** が因数定理から言えるからです。したがって、

$$
A_s(x) \cdot B_s(x) - C_s(x) = h(x) \cdot Z(x)
$$

を満たす **多項式 $h(x)$ が存在** します。証明者が知っているのは、まさにこの $h(x)$ です（前回の長除法でこれを実際に計算します）。

検証側は、**ある秘密の点 $\tau$ で両辺の値が等しいか** をペアリングで確かめるだけです。Schwartz-Zippel の補題により、これは「多項式の恒等式が成り立つ」とほぼ同じになる、という前回の話につながります。

ここまで来ると、**前回までの道具がきれいに繋がる** のが分かります。

- Lagrange 補間 → R1CS の各列を多項式に畳む
- 長除法 → $h(x) = (A_s(x) \cdot B_s(x) - C_s(x)) / Z(x)$ を実際に求める
- Schwartz-Zippel → 1 点評価で多項式の等式を検証してよい根拠

「制約の集合」が「ある多項式の割り算が割り切れる」というたった 1 本の条件に圧縮される瞬間です。Groth16 の世界観の **核** が、ようやく見えてきた気がします。

# まとめ

- R1CS の $A \cdot B = C$ という縛りは、**ペアリングが乗算 1 回しか提供できない** という Layer 3 の制約を逆算した形だった
- R1CS から QAP への変換は、**行列の「列」を Lagrange 補間する** という一手で、「制約の集合」を「多項式の組」に翻訳する操作だった
- $h(x) \cdot Z(x)$ の登場により、**「全制約を満たす」が「ある多項式の割り算が割り切れる」と等価** になり、検証は 1 点評価に集約される

前回の最後で「数学の世界で扱っていた『多項式』が、実装の世界では『データ構造とアルゴリズムの選択』として現れた」と書きました。
今回はその対句が、**「数学側の『制約 = 多項式の零点』」 vs 「実装側の『Witness ベクトルと 3 本の多項式の組の組み合わせ』」** という形でもう一段現れた感覚です。
