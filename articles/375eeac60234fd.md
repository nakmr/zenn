# なぜ有限体の演算を実装するのか？

Groth16 はペアリング pairing を使う zk-SNARK であるため、BN254 などのペアリングフレンドリーな楕円曲線を使用します。
曲線の方程式 $y^2 = x^3 + ax + b$ は素数 $p$ を法とする有限体 $\mathbb{F}_p$ 上で定義されるので、点の加算・スカラー倍を計算するには $\mathbb{F}_p$ 上の四則演算、特に逆元が必要になります。

今回は必要最低限の内容に絞って、有限体の要素 `FieldElement` と、その演算を実装しました。

# 実装中の気づき

## Rust の `%` 演算子は負数で負を返す

Rust の % は余りを求める演算子であるため、負数を割ると結果がマイナスになる。

```rust
println!("{}", -15 % 7);
// -1
```

そこで、`FieldELement` の初期化時には、負の数を正の数に引き戻す処理を加えました。これにより、負数を使った場合でも、有限体 $\mathbb{F}_p$ の要素が得られるようになります。

```rust
pub fn new(value: impl Into<BigInt>, p: impl Into<BigInt>) -> Self {
    let value = value.into();
    let p = p.into();
    // 値が 0 <= value < p の範囲に収まるように正規化
    // Rust の % は余りを求める演算子であるため、負数を割ると結果がマイナスになる。
    // そこで、「負の数」を「正の整数」に無理やり引き戻す。
    let normalized_value = ((value % &p) + &p) % &p;
    FieldElement {
        value: normalized_value,
        p,
    }
}
```

## Into<BigInt> を使ってパースする

Groth16 で利用する曲線が扱う素数 `p` (base field) または `r` (scalar field) のサイズは、BN254の場合 254 bit と、`u128` を使っても、型レベルで物理的に収まりません。
また、乗算の中間値は最大で約 `2p` bit、つまり 508 bit になることから、やはり Rust 標準の型では収まりません。

そこで、`BigInt` を利用して、可変長で大きな桁数の数を扱えるようにしました。


:::message
`BigInt` は内部が `Vec<u32>` のヒープ可変長整数です。つまり、`new()` するたびに `Vec` のアロケーションが走ります。また、可変長なので、固定幅の `u64` と比べると、演算速度は遅いです。なので、本番実装では、`ark-ff` などを利用して、処理速度にも気を配るべきです。
が、今回は学習用ということで `BigInt` を利用します。
:::

ただ、`BigInt` をメソッドの引数で型宣言してしまうと、呼び出し側で、毎回 `BigInt::from(i)` と書かなければならず、手間です。

```rust
let value = BigInt::from(5); // <- めんどくさい
let p = BigInt::from(7); // <- これもめんどくさい
let fe = FieldElement::new(value, p);
```

そこで、Rust の `Into` Trait を使って、`FiledElement::new()` の中で `BigInt` に変換するようにします。

```rust
pub fn new(value: impl Into<BigInt>, p: impl Into<BigInt>) -> Self
```

このように宣言すると、「`BigInt` に変換可能な、なんらかの型を受け取る」ということを宣言できます。

これにより、`i32`, `u64` などをそのままこのメソッドに渡せるようになり、実装がスッキリとします。

```rust
let fe = FieldElement::new(5, 7);
```

# 学んだこと

## フェルマーの小定理 vs 拡張ユークリッド法

有限体の計算のうち、割り算 を実現するために逆元 $a^{-1} \mod p$ を求める必要があります。
その方法には「フェルマーの小定理」と「拡張ユークリッド法」がありますが、アプローチが異なります。

### フェルマーの小定理

$p$ が素数で $\gcd(a, p) = 1$ のとき

$$
a^{(p-1)} \equiv 1 \mod p \\
\Rightarrow a \times a^{(p-2)} \equiv 1 \mod p \\
\Rightarrow a^{-1} \equiv a^{(p-2)} \\
$$

つまり、$a$ を $p-2$ 乗するだけで逆元になり、実装がシンプルになります。

### 拡張ユークリッド法

$ax + py = \gcd(a, p) = 1$ を満たす $x$ と $y$ を求めると、$x \equiv a^{-1} \mod p$ となる。$\gcd$ を計算する過程で、逆元が算出できる。

### なぜ拡張ユークリッド法の方が速いのか

実装では、`BigInt::modinv` を利用していますが、これは拡張ユークリッド法の実装です。

というのも、

- フェルマーの小定理
  - $a^{p-2}$ を求めるために、`BigInt` の全幅を使った乗算を $\mathcal{O}(\log p)$ 回行う
  - 例えば 256 bit なら、約 256回、256 bit 同士の掛け算が発生する
- 拡張ユークリッド法
  - 割り算と引き算が $\mathcal{O}(\log p)$ 回だけ
  - また、中間値もステップを重ねるごとに小さくなっていく

つまり、教科書的な「簡潔で美しい定理」と、「実装での合理的な選択」は必ずしも一致しない、ということです。
